# newbound_nebula

Make your personal Newbound network a virtually private one with
[Nebula](https://github.com/slackhq/nebula), Slack's open-source overlay
network. The Nebula app lets you install the nebula binary, create
networks, sign member certificates, and roll the overlay out to every
Newbound peer you have admin access to — from one UI. **No publicly
accessible lighthouse is required**: members discover each other over
Newbound's own encrypted peer network (see "The peer mesh" below).

## Install

Only your **first** instance touches git — rolling the app out to the rest
of your peers happens inside the app itself ("Install on this peer"
streams the library over the encrypted peer network; peers never need
git). To install on that first instance:

1. Open the **Dev** app → shelf → **git import**, and import
   `https://github.com/mraiser/newbound_nebula` (or call
   `dev.github.import` with that URL). The platform clones the repo into
   `repositories/nebula` and links `data/nebula` + `runtime/nebula` into
   place.
2. Restart the Newbound software once (the first install adds the
   `nebula` hot-reload crate to the build; after this one restart,
   library code updates hot-load with no further restarts).
3. Activate the **Nebula** app in the app list (or add `nebula` to the
   `apps=` line of `config.properties`).

To update: `dev.github.update` with library `nebula` (or `git pull` in
`repositories/nebula` followed by a rebuild). To uninstall:
`dev.github.remove` — your keys live under
`runtime/nebula/networks/`, so read the warning it gives you before
confirming.

## Use

Open the Nebula app:

- **Install a release** — the release list is fetched by the instance
  itself (falling back to your browser, then to a paste-a-URL box for
  offline installs); the tarball is downloaded (curl) and unpacked into
  `runtime/nebula/bin/`. Network creation stays gated until an engine
  is installed.
- **Create a network** — name, subnet pattern, port. The CA and this
  host's certificate are generated by `nebula-cert` directly into
  `runtime/nebula/networks/<name>/`; the CA key never leaves that
  folder.
- **Add members** — pick a peer, an overlay IP, and optional firewall
  groups. The member's certificate is signed here and delivered to the
  joining peer over Newbound's encrypted peer channel; the peer writes
  it into its own `runtime/nebula/networks/<name>/`, and the mesh syncs
  automatically so everyone can reach the newcomer.
- **Run it** — "Run now" launches the tunnel as a supervised child
  process of Newbound (no systemd, no sudo) and reports honestly: the
  UI shows the live running state, a Stop button, and the tunnel's own
  output when a launch fails. The "Start at boot" switch maintains the
  `start=` key of `runtime/nebula/botd.properties` for you. The systemd
  unit install remains available as a legacy option and its controls
  appear only on hosts that actually run systemd.
- **Lighthouses** — optional. Mark a publicly reachable peer as a
  lighthouse only when some members' NATs defeat the peer mesh.

All nebula commands are admin-only: they manage keys, spawn processes,
and (on the legacy path) shell out to `sudo systemctl`.

## The peer mesh — no public lighthouse needed

A nebula lighthouse does two jobs: members report their public UDP
endpoints to it, and it answers other members' queries so they can
hole-punch each other. In a Newbound fleet the encrypted peer network
already reaches every member, so the app does the discovery job itself:

- `endpoints` reports a host's own candidate endpoints and, crucially,
  the address the platform *observed* for any connected peer — the same
  post-NAT public face a lighthouse would have seen.
- **Sync mesh** (Members tab, and automatically after every join)
  gathers candidates for all members over the peer channel and pushes
  the merged map to everyone via `update_hosts`.
- `save_config` renders that map into nebula's `static_host_map` with
  `punchy` enabled on every member; nebula then dials and hole-punches
  members directly — no `lighthouse.hosts` entry required. A running
  supervised tunnel is bounced automatically when its map changes.

Members behind ordinary NATs reach each other exactly as they would via
a lighthouse-brokered punch. Pathological NATs (symmetric/port-random)
can still defeat direct punching — that is the one case where marking
some reachable peer as a lighthouse (or port-forwarding one member)
remains useful, and the UI says so.

## Security notes

- Nothing secret is ever committed or synced: private keys and network
  configs live only under `runtime/nebula/networks/<name>/`, which is
  gitignored here and stays on the instance that owns it.
- The network's CA key exists only on the instance that created the
  network. Member keys travel once, to the joining peer, over the
  already-encrypted Newbound peer channel.
- Removing a member deletes its folder but does not revoke the issued
  certificate — rotate the CA (recreate the network) to force a member
  out.

## Layout

- `data/nebula/` — the store library (source of truth): four controls
  (`nebula`, `lighthouse`, `network`, `member`) and the 21 commands.
- `nebula/` — the generated FFI dylib crate, tracked so the Rust is
  reviewable; regenerated from the store by `newbound rebuild`.
- `runtime/nebula/` — the app shell (`app.properties`, `src/html`).
  At runtime it also holds local values: the nebula binary (`bin/`) and
  your networks (`networks/`) — never committed.

## Dependencies

A working [Newbound](https://github.com/mraiser/newbound) installation,
plus `curl` and `tar` on the PATH (used to fetch and unpack nebula
releases). No third-party Rust dependencies.
